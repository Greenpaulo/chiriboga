# I7.1 ICE install versus credit and draw

**Roadmap item:** I7.1 · **Depends on:** I2, F2, F4 · **Sets:** playable sets (`documentation/card-sets.md`)
**Read first:** `documentation/ai-principles.md`, `documentation/corp-ai/principles.md`, `documentation/corp-ai/specs/install-decisions-design.md`
**Verified against code:** 376f32c (2026-09-25)

## Goal
Decide between installing the best executable ICE candidate, gaining credits
and drawing on one scale, so the Corp clicks for a credit when that credit
turns an unusable ICE into a decisive one, and protects the next server when
waiting would not help. (Split from the former I7; root installs, operations
and advancement are I7.2.)

## Current behaviour
In `Phase_Main`, ICE competes with credit and draw only through ordering:
`_criticalBreachDefenseAction()` (central loss risk), then the priority-only
install path (`priorityRankedInstallOptions[0]`), then
`_emergencyProtectionRecoveryAction()` (rez or install an `AIEmergencyDraw`
card, or draw, when a critical server has no ICE available), then economy
checks through `_bestMainPhaseEconomyOption()`.

The only credit-versus-install comparison is the hand-pressure path's "Just
need a tiny bit more cash" probe. It is effectively this item's first scenario
and it is broken: it runs only when the hand is full, adds
`this._clicksLeft() - 1` credits to `corp.creditPool` without a guard, compares
two `_rankedInstallOptions()` arrays with `<` (string coercion that works only
by accident), and asks whether more options appear, not whether a better one
does. F2 fixes the guard and the comparison; the decision itself is replaced
here.
See [architecture.md: install planning today](../architecture.md#install-planning-today).

## Design
- **Structure.** Use the design note's bands: forced and winning actions
  (band 3) and tactical safety (band 2) keep fixed priority; within band 1,
  ICE candidates, gaining credits and drawing get one comparable value in
  credit-equivalents.
- **Gain credit.** Value = 1 credit - `CLICK_VALUE` + the best increase in an
  ICE candidate's I2 score that the extra credits make executable next click
  (evaluated with a projected credit pool through `_withHypothetical()`, not by
  re-ranking whole lists). Compare against the best executable `(ICE, server)`
  candidate now, never against an abstract need to protect a server the hand
  cannot help.
- **Draw.** Value = `CLICK_VALUE` baseline plus bounded emergency value when a
  critical server has no ICE; `_emergencyProtectionRecoveryAction()` becomes
  one candidate in this comparison and keeps its agenda-flood, economy,
  last-click and imperfect-information guards.
- **Reserve.** Leave a slot for "hold" as an alternative; the R1 items (reserve
  and optionality) fill it when they land. They are not dependencies.
- Replace the hand-pressure probe with this comparison; delete it once
  scenario 1 passes through the new path.

## Safety and information boundary
Forced and game-winning actions remain hard priorities, and
`_criticalBreachDefenseAction()` keeps its thresholds. The projected credit
pool never touches live `corp.creditPool` outside `_withHypothetical()`. Hidden
Runner cards do not affect the comparison.

## Test scenarios
1. Gain-credit-then-install is preferred when the extra credit changes an ICE
   from unusable to a lockout on an insecure server, whether or not the hand is
   full.
2. Installing unaffordable ICE does not outrank funding already installed
   critical defense without explicit future value.
3. Gaining a credit is compared against the best executable `(ICE, server)`
   candidate, not against an abstract need to protect a server for which the
   hand has no viable response.
4. Protecting the second-ranked server outranks gaining a credit when the
   first-ranked server is currently infeasible and the second install has a
   positive `securityGain`.
5. With a critical server and no ICE in hand, the emergency draw path is still
   chosen, and its last-click guard still holds.

## Acceptance gate
Improvement gate: candidate `this.options.iceVersusEconomy` on against I0's
baseline (with I2's option on in both arms), with the standard guards (design
note) and:

- Improvement: `pointsStolen` per game falls (candidate minus baseline upper
  bound below 0).
- Guards: `unusedCreditsAtEnd` upper bound at most +2 credits;
  `stallTurns` upper bound at most +0.5 turns per game.
