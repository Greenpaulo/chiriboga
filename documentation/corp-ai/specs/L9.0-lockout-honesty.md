# L9.0 Lockout honesty

**Roadmap item:** L9.0 · **Depends on:** none · **Sets:** playable sets (`documentation/card-sets.md`)
**Read first:** `documentation/ai-principles.md`, `documentation/corp-ai/principles.md`, [L9 Run-simulation fidelity](L9-run-simulation-fidelity.md)
**Verified against code:** 3c25455 (2026-10-09)

## Goal
Make `_evaluateServerSecurity()` also report an honest verdict: no hard
lockout when the Runner can in fact get through, and a graded cost instead of
a collapse to `Infinity`. Today about nine in ten "secure" verdicts in real games
are lockouts that mean only "no matching breaker is installed right now", and
ICE the Runner can break by spending clicks (bioroids) is treated as
unbreakable. I2 (ICE selection by marginal security) puts most of its weight on
lockout and on the change in mandatory break cost, so on today's evaluator it
would mostly be measuring false lockouts. This item comes before I2.

## Current behaviour
Evidence from an audit on 2026-10-09 (read-only; calibration run in a scratch
copy, 700 games, `core-v1`, seeds 1-100 per pair, servers with stakes only):

- A server judged secure at the start of a Runner turn was breached that turn
  8.0% of the time; insecure 23.1%. Remotes holding an agenda: 12.0% versus
  28.3%. The verdict carries information, but leaks.
- 10,539 of 11,744 secure verdicts were "mandatory breaks with no capable
  breaker" lockouts.
- In a 20-game sample of secure, fully rezzed servers that were then breached
  (115 cases): 58 involved a bioroid (Eli 1.0, Brân 1.0), 32 had the Runner
  install a breaker that turn, and 19 were priced secure but the Runner found
  more credits than the evaluator's ceiling.

In the code:

1. **Click-breaks are not modelled.** `_matchingBreakerForIce()` looks only at
   the Runner's installed cards. A bioroid's own "Lose [click]: Break 1
   subroutine on this ice" ability (Eli 1.0 in `sets/systemupdate2021.js`,
   Brân 1.0 in `sets/systemgateway.js`) is never considered, and clicks enter
   the evaluator only as credits. Verified: Eli 1.0 against a Runner with
   4 clicks, 10 credits and no breakers gives `isSecure` and `hasHardLockout`
   both true.
2. **"No installed breaker" is a hard lockout.** In the per-ICE loop of
   `_evaluateServerSecurityUncached()` a mandatory cost of `Infinity` sets
   `hasHardLockout` with the reason "has mandatory breaks with no capable
   breaker". A Runner with 30 credits, a 5-card Grip and a 40-card Stack is
   locked out by one rezzed ETR Barrier. A test in
   `tests/corp-server-security.test.js` pins this behaviour. Once any layer is
   `Infinity`, `totalMandatoryBreakCost` is `Infinity`, so the difference that
   another ICE makes is `Infinity` or `NaN`.
3. Unpriceable breakers (Sang Kancil, Principia) are L9 limit 1 and the bug
   `sang-kancil-and-principia-priced-as-unbreakable.md`; not this item.

Every consumer reads `isSecure` (and some `hasHardLockout`):
`_protectionScore()`, `_rankedServersToProtect()`, `_iceLayerPolicy()`, the
`_centralBreachLossRisk()` early return, `_isAScoringServer()`, the rez checks
in `_iceSecurityWithAndWithout()`, and the draw and purge checks. See
[architecture: server security evaluation](../architecture.md#server-security-evaluation).

## Design
The evaluator reports the honest picture alongside today's verdict. **No
consumer changes in this item:** `isSecure` and `hasHardLockout` keep their
current values, so no Corp choice moves. Letting decisions use the honest
verdict changes strategy and is the gated follow-up
[L9.0.1](L9.0.1-adopt-honest-lockout.md); I2 reads the new fields behind its
own gate.

- **Click-breakable ICE.** Price an ICE subroutine that the ICE itself lets the
  Runner break for a click (declared by a hook on the ICE, not by title) as a
  click cost within the Runner's remaining click budget for the turn,
  converted at the evaluator's existing click-to-credit rate. Add a hook such
  as `AIClickBreakable(subroutineIndex)` (exact shape chosen at planning) on
  Eli 1.0, Brân 1.0 and every other playable ICE with a self-break ability,
  and document it in `documentation/ai.md`.
- **"No breaker yet" is not a real lockout.** Report a layer whose only
  obstacle is a missing breaker as `noBreakerLockout`, with its own reason,
  and give it a finite `breakerAbsentCost` from public information (for
  example the cheapest printed install-plus-break cost among the Runner's
  public breakers of that type, else a documented constant).
- **New result fields:** `honestLockout` (a lockout that survives both
  corrections), `honestMandatoryBreakCost` and `honestBreakCost` (finite
  whenever no honest lockout exists), `honestIsSecure`, and
  `noBreakerLockout`. Today's fields are computed exactly as now.
- **Calibration collector.** Build the audit's scratch collector properly:
  `headless.js` records a per-server security snapshot (today's and the honest
  verdict) at the start of each Runner turn and the server name on `run`
  events; collector `securityCalibration` reports the next-turn breach rate of
  servers judged secure and insecure under each verdict. L9.0.1 uses it.

## Safety and information boundary
- Public information only: installed Runner cards, public pile sizes and
  Runner cards already seen. Never Grip or Stack identities.
- Every existing consumer's input stays unchanged.
- Evaluation stays read-only and inside the existing hypothetical guards.

## Test scenarios
1. Eli 1.0 rezzed, Runner with 4 clicks, 10 credits and no breakers:
   `honestIsSecure` false and `honestLockout` false, with a reason naming the
   click-break; `isSecure` and `hasHardLockout` unchanged (true).
2. The same with the Runner on its last click and two ETR subroutines: one
   click breaks only one subroutine, so `honestIsSecure` stays true, with a
   reason saying why.
3. A rezzed ETR Barrier and a Runner with no Fracter: `noBreakerLockout` true,
   `honestLockout` false, a finite `breakerAbsentCost` and
   `honestMandatoryBreakCost`; `isSecure` unchanged.
4. A route with a click-breakable layer and an ordinary layer the Runner can
   pay for: the honest totals combine (clicks within budget, credits within
   the ceiling).
5. Changing hidden Grip or Stack cards changes nothing.
6. Every decision fixture and decision snapshot is identical, and every
   existing case in `tests/corp-server-security.test.js` passes unchanged.
7. The `securityCalibration` collector, driven through a scripted sequence,
   counts a breached secure server and an unbreached insecure server under
   both verdicts.

## Acceptance gate
N/A — deterministic fix (principle 4): observation-only invariant. No
consumer's input changes, so decision snapshots match the baseline exactly and
I0's F4 configuration reproduces its per-game `winner`, `turns`, `logHash` and
`decisionHash`; the new fields follow the game rules (a bioroid's printed
self-break ability) and public information, checked by scenarios 1-5.

## Things to consider
- Running both verdicts costs evaluator time on every call; measure
  `decisionLatencyMs` in the identity run. If it is material, compute the
  honest fields only while recording or when a caller asks.
- The 19 "priced secure but breached" cases point at the credit ceiling
  leaving out economy events still in the Grip (inferred, not verified).
  That belongs to a separate item if confirmed.
- `structuralRisk` and `publicThreatRisk` are computed only for one-ICE
  servers; I2 should not assume they are present on deeper servers.
