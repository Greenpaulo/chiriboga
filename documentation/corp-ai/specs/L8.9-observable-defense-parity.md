## Goal

Identify the decision mechanisms behind the remaining agenda-to-ICE tell,
then implement and gate a supported repair in this same ticket. Investigation
is the first implementation phase, not a separate ticket hand-off. Do not
preselect a parity formula before observing the adopted L8.2/I2 policy.

[F12](../../backlog/code-review/F12-realized-defense-measurement.md) owns `realizedIceByRootType`;
I2 consumes it with its own count guards. L8.9
uses its [shared definitions and readiness rules](../../ai-batch-harness.md#realized-defense-measurement-f12) and
extends those shared observations after I2 finishes; it does not duplicate the collector
or hold up I2. Prefer completing attribution and any adopted repair before
I3's design/gate is frozen because
placement findings can affect remote-role suitability. That is a sequencing
preference, not a formal I3 prerequisite.

## Current behaviour

- `_remoteDeceptionProfile()` draws a shared lifetime shape for agendas,
  Ambushes and declared access-punishing cards. Baseline target depths have
  probabilities 30/48/22 percent for 1/2/3 ICE; the optional match-local feedback
  policy can adjust the shared distribution.
- `_NoMoreProtectionForThisServer()` stops extra ICE once an active posture's
  target depth is reached. Shared profile rolls alone do not equalise realized
  ICE count across classes.
- Posture eligibility and rates differ. `_shouldBluffAgendaServer()` requires
  a single hidden advanceable agenda and uses agenda points in its rate;
  `_shouldBaitServer()` uses installed punishment severity and root count.
  Both retain winning-breach guards. Bait eligibility is not currently restricted
  to single-root servers in the same way as agenda bluffing.
- HVT install options are sorted by advancement-limit/scoring-window distance
  plus `0.75 * _deceptionInstallDistance()`. `_advancementLimit()` may return
  Infinity; `_scoringWindow()` depends partly on protection relative to HQ.
  `_isAScoringServer()` recognises existing agendas and Ambushes, but actual
  candidate eligibility, overwrite rules and sort inputs still matter.
- I2 remains proposed at this stamp. Its spec requires common ordinary ranking
  for equivalent active agenda/trap postures and true consequences elsewhere,
  plus all-server and postured count guards. Those are planned requirements,
  not an implemented marginal scorer or measured residual.
- L8.4's recorded smoke finding motivates investigation; its historical rho
  is not a current full-pool measurement or proof of one causal explanation.

## Design

### Passive attribution

Extend F12's delivered observations with commitment IDs and records of the
values already used by actual decisions. At a root install, capture eligibility,
selected and alternative destinations, pre-install ICE counts, actual sort rank,
advancement limit, scoring window, protection score, existing profile distance,
posture/safety state and choice reason. Capture later ICE installs/removals,
posture transitions and each Runner-turn snapshot. Represent Infinity explicitly
in exported data. Label evaluator-derived security as Corp-known assessment,
not as information visible to the Runner about unrezzed ICE.

Instrument existing evaluation results; never re-sort options or call a posture/
profile helper to obtain a diagnostic that would roll or cache new state. An
uncomputed input is `unknown`, not a reason to evaluate a new decision path.
Record start-board commitments with left-censoring metadata; unknown original
placement is not invented. Root classes are harness-only truth labels, defined
by agenda type or Ambush/access-punishment declarations, not card-title lists.

Report both the existing snapshot statistic and commitment-level distributions:

- ICE present when each root was installed;
- subsequent ICE added/removed during comparable root-age windows;
- postured/unpostured, single/multi-root, revealed/unrevealed and safety cases;
- agenda/trap commitment counts, usable games and lifecycle endpoints (score,
  steal, overwrite, trash, game end).

Agendas can leave through scoring while traps persist. Repeated snapshots
therefore measure exposure, not independent placements. Cluster uncertainty
within games; report age-stratified and one-observation-per-commitment results
so survival differences are visible. Multi-root observations share one defense
and must not be treated as independent servers. Revealed roots are diagnostic,
not hidden-class tells. Keep safety overrides in headline coverage and identify
rather than discard them.

### Attribution and disposition

Run control-only `--quick`, then 200 seeds per committed deck pair with the
current adopted options recorded. Separate these hypotheses:

1. Candidate availability/eligibility or placement already differs at install.
2. Class-dependent posture eligibility/rates change capped-server shares.
3. Later unpostured protection decisions create or widen the gap.
4. Root survival, draws, multi-root mechanics or revealed cards explain residue.

Use temporal records to distinguish an observed association from a mechanism
actually exercised in a decision. Observational splits need not produce additive
causal percentages. If evidence is ambiguous, state what experiment would resolve
it rather than claiming an exact attribution. Controlled diagnostic experiments
may proceed after their hypothesis, options and measures are recorded in this
ticket, before examining their candidate results.

### Repair in the same ticket

Record an attribution table, then choose the smallest supported change to
placement, posture eligibility or later ICE allocation. Document its root cause,
scope, named score components and deterministic acceptance scenarios here before
implementation. Follow the ordinary implement-ticket planning rules for risky
changes; no second ticket is required. Keep the repair behind default-off
`observableDefenseParity`. If the repair belongs to placement, coordinate its
boundary with I3 so the same rule is not implemented twice.

Preserve tactical safety and equivalent agenda/trap active-posture ranking.
Do not equalise raw counts by wasting ICE or removing necessary agenda defense.
Do not condition decisions on harness-only labels or private Runner information.
Sampled agenda requirements do not prove placement parity, public-variable
posture rates can introduce new tells, and L8.2's single-root policy does not
erase multi-root observations. Attribution determines the design, not exemption
from the improvement gate.

If there is no worthwhile repair or evidence remains insufficient, record that
result in this ticket and leave the policy unadopted. Do not claim tell reduction
or silently complete the implementation objective from observation alone.

## Safety and information boundary

The passive attribution phase must not change policy RNG, profile/posture caches, hypothetical
state, candidate order or gameplay logs. Hidden Runner identities are never
inputs. Existing tactical safety is authoritative; lower raw class correlation
is not sufficient justification for wasting protection or risking agendas.

## Test scenarios

1. Scripted agenda/trap installs reconcile decision inputs and install ICE
   counts with subsequent snapshots and F12's existing collector totals.
2. An unavailable destination is distinguished from an eligible low-ranked one;
   Infinity and missing inputs export without invented finite scores.
3. Scoring an agenda and retaining a trap produces a snapshot/commitment
   difference that is explained by lifecycle records, not extra allocations.
4. Later ICE placement/removal and genuine posture transitions are recorded
   once; observing an unrolled posture consumes no RNG or creates no cache.
5. Multi-root, revealed, safety and left-censored start cases retain their
   labels and do not silently disappear from relevant coverage.
6. Hidden Runner substitutions and throwing observation code leave policy
   state, decisions and gameplay logs unchanged.
7. Game-clustered summaries reproduce known scripted counts; absent root
   classes and thin cohorts report insufficient evidence rather than success.
8. Add deterministic cases from the identified decision mechanism: the repair
   changes the implicated choice, preserves equivalent active agenda/trap
   ranking and retains winning-breach guards. Repeated/hypothetical queries
   preserve RNG/cache lifetimes; option-off retains adopted policy behavior.
9. The repair cannot manufacture a passing tell metric by dropping safety,
   multi-root, unpostured or unknown cases from headline coverage.

## Acceptance gate

Two phases in this ticket. Passive instrumentation first proves identity:
with observation disabled/enabled on the same adopted L8.2/I2 revision, run
200 paired seeds per committed deck pair. Successful pairs match winner, turns,
logHash and decisionHash, with no new failures or policy RNG/cache changes.
Record effective prerequisite options, coverage and exact observation commands.
Insufficient observations are not evidence that the tell is absent.

The repair is strategic and requires an F4 adoption gate. Option
`observableDefenseParity` defaults off; baseline off, candidate on. Use a fresh
matching control, committed deck pool, initially 200 paired games per deck pair,
F11's game-paired pooled bootstrap 95% intervals and F12's metric definitions.
Collectors: `realizedIceByRootType`, `bluffSingleVariableCorrelation`,
`installOutcomes` (diagnostic). Starts: none initially; if coverage or option
reachability is insufficient, add fixed real-game-derived starts and a separate
gate, with every command required to pass. Freeze coverage, sample size, starts
and all guard margins from control-only evidence before repair implementation
or viewing policy candidate results.

| Check | Metric | Better | Threshold |
|---|---|---|---|
| Improve | `realizedIceByRootType.allCountDistance` | lower | paired candidate-minus-control 95% upper bound < 0 |
| Guard | `realizedIceByRootType.posturedCountDistance` | lower | calibrated regression margin; freeze before implementation |
| Guard | `realizedIceByRootType.allCountCorrelation` | lower | calibrated regression margin; freeze before implementation |
| Guard | `realizedIceByRootType.posturedCountCorrelation` | lower | calibrated regression margin; freeze before implementation |
| Guard | `bluffSingleVariableCorrelation.max` | lower | calibrated regression margin; freeze before implementation |
| Guard | `winRate` | higher | regression at most 0.02 |
| Guard | `pointsStolen` | lower | regression at most 0.2 |
| Guard | `pointsScored` | higher | regression at most 0.2 |

Gate command core (not runnable as the full gate until calibrated pooled guards
are added): `node scripts/ai-batch.js gate --fresh --corp-option observableDefenseParity=true --collector realizedIceByRootType --collector bluffSingleVariableCorrelation --collector installOutcomes --improve realizedIceByRootType.allCountDistance --guard winRate=0.02 --guard pointsStolen=0.2 --guard pointsScored=0.2`.
Add all frozen guard rows and any required starts before gate execution. Do not
copy a rho margin into TV units or relax a threshold after candidate results.

Report residual tell size, class/count distributions, root ages/lifecycles,
per-deck breakdowns, both arms' intervals and paired differences. Metrics must
be valid with adequate agenda/trap/game coverage; unknowns and safety cases stay
visible. A targeted mechanism can be tested separately, but a successful subset
cannot replace the headline all-root improvement after seeing results. Failure
to demonstrate reduction or pass a guard blocks adoption of the repair.
