## Goal
Gates whose option matters only on boards the deck pool rarely reaches need
start boards. Today each ticket hand-builds them, which caused avoidable
errors on
[corp-silently-declines-rez-of-ice-hosting-a-trojan.md](../../bugs/corp-silently-declines-rez-of-ice-hosting-a-trojan.md):
boards were edited until the option fired, and one board per named card made
gate cost grow with the number of boards. F10 makes start boards come from real
games, built by a tool, stored in one shared library, and run under a fixed
game budget. Every board-based gate then costs the same (one baseline and one
candidate run, about 8 minutes each) and tests real positions.

## Current behaviour
- `node scripts/ai-batch.js --start <fixture|dir>` begins every game from a
  corp-decision fixture board. The pool's decks fill R&D and the Stack unless
  the fixture lists them, and `resolveStarts()` rejects cards outside the
  pool's trusted sets.
- A gate runs every start × every pair × 200 seeds. Each extra board adds
  1,400 games per half (about 8 minutes).
- Metrics pool across all `--start` boards in one command, so a per-board
  check needs its own command.
- Start boards are hand-written by each ticket under
  `tests/fixtures/ai-batch/starts/`, typically by editing a log's
  `RunnerTestField`/`CorpTestField` dump with `sed`. Nothing checks which
  changes were made. "Start boards come from real boards" in
  `ai-planning.md` states the rule, but no tool enforces it.
- A debug log's dump is the end-of-log state, not the decision-time state.
  Rebuilding the board before the decision (an agenda that was stolen at the
  decision, for example) is manual.

## Design

### Builder: `scripts/start-board.js`

```
node scripts/start-board.js <log> (--snapshot <n> | --dump) --out <name> [edits]
node scripts/start-board.js <log> --list
```

- **Source, chosen explicitly:**
  - `--snapshot <n>` uses decision snapshot `n`, the decision-time board,
    parsed with `parseSnapshots()` from `tests/extract-fixture.js`. `--list`
    prints the snapshots, as `extract-fixture.js --list` does.
  - `--dump` uses the end-of-log `RunnerTestField(...)`/`CorpTestField(...)`
    dump and the lines after it, up to the `Version reference` line.
  - Use `--snapshot` whenever the log has snapshots. Without either flag the
    builder exits with an error that lists the snapshots.
- **Output:** `tests/fixtures/ai-batch/starts/<name>.txt`, in corp-decision
  fixture format with no `EXPECT`. It carries `// SOURCE:` (the log path and
  `snapshot <n>` or `dump`), one `// NOTE:` line per edit, and `// TAGS:`.
  It refuses to overwrite an existing file unless `--force` is given.
- **Allowed edits.** These are the only ones; each needs `--reason "<text>"`
  where marked, and writes a `NOTE` line:
  1. `--replace <fromId>=<toId> --reason "<text>"`: replaces every copy of a
     card. Refused when `<fromId>` is in the Runner's rig or hosted on ICE.
     The reason must say the card crashes the engine or is outside the pool's
     trusted sets. Replacing installed ICE is allowed, because a crashing
     ICE is a real case (Scatter Field on HQ in the source log), and the note
     names the servers where it was installed, so a reviewer can judge
     whether it touches the decision.
  2. `--unsteal <agendaId>=<serverIndex>`: moves an agenda from the Runner's
     score area back into that remote's root, and `--unscore` does the same
     for the Corp's. Only for `--dump`, to restore the board before the
     decision.
  3. `--setup "<statements>"`: credits and clicks only. Each statement must
     match `^(corp|runner)\.(creditPool|clickTracker)=\d+$`. It is written
     as the fixture's `// SETUP:` line.

  Anything else (a hand edit, or a flag outside this list) is not a start
  board. The test suite rebuilds every committed board from its recorded
  `SOURCE` and `NOTE` flags and fails on any difference.
- **Recorded flags:** each `NOTE` line ends with the exact flag that made it,
  in the form `[--replace 35042=30072]`, so a board can be rebuilt.

### Tags

`// TAGS:` is a comma-separated list, computed when the board is built by
loading it headlessly (`playGame()` with `start` and a probe `setupFile`, as
in `tests/hosted-threat-rez-gate-setup.test.js`) before any turn is played.
The fixed vocabulary:

| Tag | Present when |
|---|---|
| `hosted-card-on-ice` | any installed ICE has a non-empty `hostedCards` |
| `unrezzed-ice` | any installed ICE is unrezzed |
| `breaker-installed` | the Runner's rig has a program with the `Icebreaker` subtype |
| `agenda-in-remote` | a remote root holds an agenda |
| `tagged-runner` | `runner.tags > 0` |

A new tag is added to this table, and to the builder, in the change that
first needs it.

### Selecting boards and the game budget (`ai-batch.js`)

- `--start-tag <tag>` (repeatable) selects every board under
  `tests/fixtures/ai-batch/starts/` whose `TAGS` include all the given tags,
  sorted by file name. It combines with `--start`.
- `--budget <games>` sets the seeds per board and pair to
  `max(10, floor(games / (boards × pairs)))`, written as `--seeds 1-<k>`, so
  every board and both halves use the same seeds and pairing is unchanged.
  It is an error to combine it with `--seeds`, `--games` or `--quick`. It is
  opt-in, so existing commands, cached baselines and the committed baseline
  are unaffected. The report records the budget and the resulting seeds,
  which are already part of the cache key.
- Board gates use `--budget 1400`, so their cost stays at one baseline and
  one candidate run however many boards match.

### Reaching the decision

There is no separate reachability check. Use `node scripts/ai-batch.js
replay --start <board> ... --diff` (`documentation/ai-batch-harness.md`):
the board reaches the option when the first differing hunk is the decision
the option targets.

## Safety and information boundary
Boards are game states; nothing here feeds hidden information to either AI.
The builder copies the dump's hidden cards (R&D order, the Stack) as the
engine recorded them, exactly as fixtures do today.

## Test scenarios
1. `--snapshot 1` and `--dump` on a committed fixture log each produce a board
   that loads under `--start` with no engine errors. Its card lists equal
   the source's, apart from the recorded edits.
2. `--replace` without `--reason`, or on a card installed as ICE or in the
   Runner's rig, exits with an error and writes nothing; a `--setup`
   statement outside the pattern is refused.
3. Every committed board under `tests/fixtures/ai-batch/starts/` rebuilds
   byte-for-byte from its `SOURCE` and recorded `NOTE` flags.
4. Tags are computed correctly on boards built to have, and to lack, each tag.
5. `--start-tag` selects exactly the matching boards, in file-name order.
6. `--budget 1400` over 2 boards and 7 pairs plays seeds 1–100 for every
   board and pair in both halves. With `--seeds` it is an error, and without
   it the existing commands' reports are unchanged (same cache key).
